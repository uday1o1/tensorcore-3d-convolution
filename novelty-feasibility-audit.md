# AI Novelty and Feasibility Audit: Tensor Core Accelerated 3D Convolution for Medical Image Segmentation

This audit follows two adversarial passes, novelty and feasibility, searching actively for reasons the idea fails or already exists rather than reasons it works. This version reflects a retargeting from MedNeXt's `conv1` to nnU-Net's dense 3D U-Net, made after layer-wise FLOP analysis showed `conv1` accounts for only 6.2% of MedNeXt's total FLOPs, too small a share to justify the kernel engineering involved.

## AI Critique Summary

Is this genuinely novel? Yes, narrowly, and the retargeting does not weaken this. Memory-efficient, Tensor-Core-targeting convolution is not a new idea: it has been developed across four real papers from 2023 to 2026 by the same research group. What has never been done, confirmed by reading all four papers in full text, is extending that specific technique beyond standard two-dimensional convolution; this claim is about the technique itself and is unaffected by which downstream architecture it is deployed into. A direct search for competing work on this specific combination, Tensor Core or windowed convolution acceleration applied to nnU-Net or to medical segmentation more broadly, found no matches: the closest result is NVIDIA's own "optimized" nnU-Net for PyTorch, which uses standard automatic mixed precision and TF32 on ordinary `Conv3d` calls, the same cuDNN baseline this project's efficiency claim is measured against, not a competing windowed-kernel implementation. A second search for "windowed convolution" or "im2win" alongside medical image segmentation found no three-dimensional or medical-segmentation-specific application of the technique; the one tangential Im2win result found is about a 2026 ARM CPU port, a different axis of extension (hardware platform, not dimensionality) that does not compete with this project's claim. The main risk to disclose honestly: the seed technique's own evaluation is a synthetic microbenchmark with no trained model behind it, so this project's real contribution is closing that gap by integrating the technique into an actual trained, evaluated system. A second risk: this field moves quickly, so the specific three-dimensional gap should be re-verified immediately before final submission, not assumed stable.

## Novelty Audit: Survives with Named Limitations

**Why it survives.** Four papers spanning 2023 to 2026, all from the same research lineage, were read in full text and confirmed to cover only standard two-dimensional convolution. Retargeting from MedNeXt to nnU-Net changes which architecture demonstrates the technique, not what is original about the technique; the 2D-to-3D extension claim is verified against Im2win's own publication history, independent of deployment target. A fresh search specifically for the new target (Tensor Core acceleration of nnU-Net, and windowed convolution in medical segmentation generally) found no competing work; the search methodology's ability to find real competing work when it exists was already confirmed in the original audit (an April 2026 depthwise-convolution CUDA optimization paper was found this way), so the absence of a hit here is informative, not just an artifact of a narrow query.

**Named limitation 1.** This is a narrow, single-lineage extension of one technique to one additional dimensionality, not a general architectural claim, and should be presented that way rather than as a broad "faster 3D deep learning" claim.

**Named limitation 2.** The technique's own published evaluation is a synthetic microbenchmark across twelve layer shapes, with no real dataset or trained model behind it. This project's contribution is specifically closing that gap, and this should be stated directly rather than implied.

**Named limitation 3.** This research area changes on a timescale of weeks rather than months. A search for closer work is repeated immediately before submission.

**Named limitation 4.** Efficiency alone is one improvement category; the project also includes an architectural experiment using the efficiency gain's freed compute to test a larger kernel size than nnU-Net's standard 3, satisfying the two-category requirement with a change genuinely enabled by the first.

**Named limitation 5.** The choice of nnU-Net as the modification target, rather than MedNeXt, was made from a compute-share argument (99.6% of FLOPs are in dense `Conv3d`, verified via `FlopCountAnalysis`) rather than an accuracy or architectural-interest argument. nnU-Net's plain 3D U-Net is a less parameter-efficient, older-design architecture than MedNeXt; this project's contribution is squarely about convolution kernel efficiency, not about advancing segmentation architecture design, and should be presented that way rather than implying nnU-Net was chosen for its own merits.

## Feasibility Audit: Survives with Named Limitations

Based only on verified resource facts, not duration estimates.

**Code and technique access.** The Im2win codebase is real, substantive, Apache-2.0 licensed, and actively maintained. Its repository contains only forward-pass CUDA kernels; no backward pass exists for training. Wrapping a working forward kernel as a PyTorch extension is a standard, well-established procedure, but this project also has to design and implement the backward kernels itself and wrap both directions in a custom autograd function, since nnU-Net is trained end to end and no reference backward implementation exists to build from. This is real engineering risk beyond the 2D-to-3D port, and is treated as such rather than folded into the "standard wrapping" claim.

**Baseline access.** All three baselines have real, substantive code. nnU-Net is actively maintained; the specific v1-lineage codebase used here (bundled inside MedNeXt's own repository, since MedNeXt is itself a modified nnU-Net v1 fork) is directly usable and was verified to build, run a forward and backward pass, and profile correctly on the project's actual GPU. MedNeXt's repository is complete and directly usable but not under active development, last pushed November 2024; it remains in the project as an unmodified reference baseline. EffiDec3D's repository is official and was pushed as recently as December 2025, satisfying the course's recency requirement; its license, marked "Other," is confirmed before use.

**Data access.** The Medical Segmentation Decathlon is fully public with no registration, application, or approval process. Verified directly: 131 labeled training volumes and 70 unlabeled test volumes for the Liver task (Task03), downloaded, extracted, and converted to nnU-Net's task format on the project's actual rented GPU instance.

**Compute access.** No GPU architecture compatibility risk is expected, since the technique's original evaluation and this project's target hardware are from the same generation family (RTX 3090). Verified directly on the project's rented instance: nnU-Net's plain 3D U-Net at the project's actual 128-cubed patch size uses 2.12GB peak inference memory and 4.80GB peak training memory at batch size 1, comfortably within a 24GB GPU's budget with room for larger batch sizes, in contrast to MedNeXt at the same patch size, which used 17.12GB at batch size 1 and ran out of memory at the planner's own recommended batch size of 2 without mixed precision. This is a feasibility improvement from the retargeting, not a new risk.

**Named limitation 1.** Im2win has only ever been tested on 2D kernel shapes (up to size 11 in a single spatial dimension); nnU-Net uses 3D kernels at size 3. The open question is dimensionality, not size, since the windowing scheme has never been exercised on a genuinely three-dimensional kernel at any size. This should be checked in the first week of implementation, before committing to full-scale training runs.

**Named limitation 2.** nnU-Net's plain 3D U-Net has a wider range of convolution channel widths across its stages (32 to 640, verified directly) than MedNeXt's `conv1` would have had (32 to 512). Im2win's published kernels are hand-tuned per problem shape with compile-time tile constants, not a single shape-generic kernel; covering this wider range may require either a shape-adaptive design or multiple tuned tile configurations rather than one, which is more implementation work than a single fixed shape would need.

**Named limitation 3.** nnU-Net's plain 3D U-Net has substantially more total FLOPs than MedNeXt at the same patch size (479.0 GFLOPs versus 169.4 GFLOPs, both verified), meaning more total compute is needed to train it to convergence regardless of which convolution kernel is used. This affects the resource budget for the full training and benchmarking sweep, though it does not affect per-kernel correctness or the efficiency comparison itself, since both configurations being compared use the same architecture.

**Named limitation 4.** The backward-kernel implementation (see Feasibility, Code and technique access) has no existing reference to validate against beyond standard gradient-checking against PyTorch's autograd on small synthetic inputs. This is the single highest-risk implementation step in the project and is scheduled early, before any full training run depends on it.
